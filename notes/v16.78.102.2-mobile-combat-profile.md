# Profilage mobile V16.78.96 → V16.78.102.1

Révisions comparées :

- V16.78.96 : `22c963d`
- V16.78.102.1 : `33080b5`

## Constat

Les deux révisions ont exactement le même `index.html` (`3cf875ef5718d816a0fd8e000a2615916445ac11`). La lenteur n'est donc pas causée par une modification des règles de combat entre ces deux révisions.

Le chemin exécutable commun conserve deux coûts très visibles sur mobile :

- le lancer D6 réécrit chaque face dans le DOM toutes les 80/105 ms et ne termine une attaque à trois dés qu'après environ 2 060 ms ;
- le D100 réécrit sa valeur toutes les 90 ms et ne rend la main qu'après environ 1 080 ms ;
- un rendu de combat redemande plusieurs fois les mêmes caractéristiques, bonus d'équipement, bonus de set et statistiques ennemies ;
- le bridge UI V100 pouvait, lorsqu'il était chargé, raccorder les renderers de statistiques aux rescans de l'interface et lancer un polling de démarrage toutes les 100 ms.

Avec un CPU mobile ralenti, les intervalles de dés, les calculs répétés et les reconstructions du combat se disputent le thread principal. Les timers prennent alors beaucoup plus longtemps que leur durée nominale.

## Correction V16.78.102.2

- animation D6/D100 par `transform: translate3d()` ; aucune boucle `setInterval` et aucune écriture DOM par frame ;
- résultat final et mathématiques inchangés ;
- callback D6 mesuré à 498 ms contre 2 060 ms pour trois dés dans l'ancien chemin ;
- callback D100 mesuré à 473 ms contre 1 080 ms ;
- cache des valeurs dérivées par héros et génération de combat ;
- invalidation uniquement avant une vraie mutation d'état, jamais sur un simple rendu ;
- retrait des hooks UI placés sur `renderDungeonHeroStats` et `renderDungeonAttributes` ;
- suppression du polling UI répété pendant les premières secondes.

Le garde de régression vérifie aussi qu'une sauvegarde ou une application de dégâts invalide immédiatement les valeurs mémorisées.
